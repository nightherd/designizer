A time-series store that stays out of your way.

plumb keeps metrics, sensor readings and event streams in one file-per-shard layout, compresses them to about 1.3 bytes a point, and answers queries in plain SQL. One binary. No cluster to babysit before you need one.

01 — Model

Points, series, shards.

A point is a timestamp, a float, an integer, a bool or a short string, attached to a series. A series is a metric name plus a set of tags. That is all the data model there is, and it matches what most teams already have in their heads.

Each shard covers a fixed window of time and is written once, sorted, and then compacted. Old shards are immutable, which is why reads never lock and why backups are a cp of a directory.

Tags are indexed as bitmaps per shard. Filtering a billion series down to the twelve that belong to one service takes a few microseconds of set intersection, not a scan.

Late-arriving points are accepted for up to a configurable window. Anything older goes to a quarantine table instead of silently rewriting history.

02 — Query

It is SQL. The time parts are real.

-- p99 per minute, last 14 days
SELECT time_bucket('1m', ts) AS minute,
       quantile(0.99, latency_ms) AS p99
  FROM http_requests
 WHERE service = 'checkout'
   AND ts > now() - INTERVAL '14 days'
 GROUP BY minute
 ORDER BY minute;

Supported: time_bucket, locf and interpolate for gaps, quantile and histogram with exact or sketch modes, and asof joins between two series. There is no general-purpose join planner. See the limits below.

04 — Install

Running in under a minute.

Homebrew 
brew install plumb-db/tap/plumb
Docker 
docker run -p 7420:7420 -v $PWD/data:/data ghcr.io/plumb-db/plumb
Write a point 
# name,tag=value field=value timestamp
plumb write 'latency,service=checkout p99=41.2'
Query it 
plumb sql "SELECT * FROM latency LIMIT 5"
05 — Limits

What plumb is not good at, yet.

  1. Not a general SQL engine. Joins are limited to asof and one hash join per query. If you need to join your metrics against a customer table with forty columns, use something else for that step.
  2. One writer per shard. Ingest scales across shards and across nodes in a replicated setup, but a single hot series saturates one writer. Fan the series out with a tag if you hit this.
  3. Retention is by day. You can expire data at day granularity. Expiring individual points or tag values after the fact is not supported and is unlikely to be.
  4. Clustering is young. Replication works and is tested under partition. Automatic rebalancing is in the 1.0 milestone and not in this release.
